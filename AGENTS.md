# AGENTS.md · f2b

Guide for coding agents. What it is, how it is installed and how it is configured is in `README.md` (and `README.es.md`); the contribution guide is in `CONTRIBUTING.md`.

## What it is

TypeScript service on Node.js that follows the fail2ban log and sends bans, permanent bans and unbans to Telegram. It keeps a counter (daily, repeat offenders and total) that resets at local midnight. It has two transports: direct Bot API (`TRANSPORT=direct`) and a local tg-gateway (`TRANSPORT=gateway`). **It has no runtime dependencies**: only Node and, for building, esbuild in development.

## Architecture

Hexagonal. `src/index.ts` is the only composition root: it knows `domain`, `application` and `infrastructure` at the same time. It exports `createRuntime` to mount it in tests and only starts when run as the main program.

- `src/domain/`: entities (`fail2ban-event`, `counter-state`, `incoming-update`, `telegram-message`), ports (`event-source`, `notifier`, `update-source`, `counter-store`, `logger`) and pure services (`parse-fail2ban-line.ts`, `batch-buffer.ts`, `batch-window.ts`, `batch-summary.ts`, `counter-rules.ts`, `message-format.ts`, `shutdown-suppressor.ts`, `format-time.ts`).
- `src/application/`: use cases. `notify-fail2ban-events.ts` (instant or batched), `handle-command.ts`, `show-counter.ts`, `reset-counter.ts`, `daily-reset.ts`, `error-text.ts`.
- `src/infrastructure/`:
  - `fail2ban/tail-log-source.ts`: follows the log; detects rotation by size and inode.
  - `telegram/direct/`: `direct-notifier.ts` and `poller-update-source.ts` (long-polling).
  - `telegram/gateway/`: `gateway-notifier.ts` and `webhook-update-source.ts` (receives what the gateway forwards).
  - `telegram/normalize-update.ts`: normalizes updates from both transports.
  - `persistence/`: `file-counter-store.ts` (default) and `postgres-counter-store.ts` (optional, requires `pg`).
  - `config/env.ts`: `loadConfig()` validates everything at startup and throws `ConfigError` with the list of errors.
  - `logging/logger.ts`.

Flow: `TailLogSource` → `NotifyFail2banEventsUseCase` → `NotifierPort` (chosen transport). Commands come in through `UpdateSourcePort` → `HandleCommandUseCase`.

## How to test a change

- Tests in `tests/`, with Vitest. Config: `vitest.config.ts`, includes `tests/**/*.test.ts`; coverage is measured over `src/**/*.ts`.
- Organised by layer: `tests/domain/`, `tests/application/`, `tests/infrastructure/`, `tests/e2e/`. Helpers in `tests/test/helpers.ts` (`createTestLogger`, `jsonResponse`, `makeTempDir`).
- HTTP integration tests start a local fake server instead of touching the Bot API. Keep that pattern.
- A single file: `pnpm vitest run tests/domain/parse-fail2ban-line.test.ts`. Filter: `pnpm vitest run -t "<text>"`.
- Every new behaviour or fixed bug comes with its test in the same change. Batch bugs have regression tests in `tests/application/notify-instant-regression.test.ts` and `batch-notify.test.ts`: read them before touching `batch-*`.

## Conventions

- Package manager: **pnpm** (`pnpm-lock.yaml`, `pnpm-workspace.yaml`).
- Imports with the `.ts` extension (`allowImportingTsExtensions`). Code and comments in English; the strings the user sees are in `message-format.ts`, with `es` and `en` translations.
- Style: `eslint.config.js`.
- Commits with Conventional Commits (`feat`, `fix`, `docs`, `chore`...), in the style of the history.
- Version and `CHANGELOG.md`: generated by `commit-and-tag-version` (`.versionrc.json`) with `pnpm release`. **Not edited by hand.** `CONTRIBUTING.md` asks for changes to be noted under `[Unreleased]`, which does not fit this flow: confirm it before following it.
- Configuration: `.env` (not versioned) based on `.env.example`. No `dotenv`: the process loads `.env` with Node's native loader if it exists.

## Decisions and pitfalls

- **Command registration in the gateway.** `GATEWAY_COMMANDS` in `src/index.ts` is a fixed list: `/f2b`, `/chat_id`, `show_counter` and `not_touch`. **Do not add `/start` or `/help`.** The gateway registers by exact match and could take those commands away from another service. In `direct` they are handled, because the poller manages them.
- **False unbans when fail2ban stops.** fail2ban emits a flood of `Unban` events on shutdown. `F2B_SUPPRESS_SHUTDOWN_FLUSH` (true by default) suppresses them with `shutdown-suppressor.ts`.
- **Batch mode.** Windows are aligned to the local clock, and `BATCH_WINDOW_SEC` must divide 86400. `NOTIFY_INSTANT_JAILS` skips the batch and is **not** counted in the summary. `NOTIFY_UNBANS=list` only adds IPs with `BATCH_SHOW_IPS=true`.
- **Counter.** By default it is a JSON file in `./data/` (`COUNTER_FILE`), with no database. `COUNTER_BACKEND=postgres` requires the optional `pg` package; if the package is missing, there is no verification that startup detects it (I have not checked this).
- **Daily reset.** `daily-reset.ts` resets the counter at local midnight. The order of the summary with the daily reset has its own commits (`c6e4081`, `44f6dde`); read the history before touching it.
- **Log rotation.** `tail-log-source` detects rotation by size and by inode. If you change the reading, test both cases.
- **Configuration error = exit.** An invalid value exits with the list of errors; it does not start halfway.
- **Unit example.** `deploy/f2b.service.example` is a template (example user and paths). Adapt it in the deployment environment; do not copy it with the example values.
